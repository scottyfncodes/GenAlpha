# GenAlpha Character Art Production-Method Decision

**Status: DESIGN LANGUAGE approved and converged. PRODUCTION METHOD decided
by this document. No production art produced by this document.**

This document answers the one question `genalpha-character-production-brief.md`
§19 deliberately left open: *how* the approved Direction A ("Soft Chibi")
design gets turned into a real, shippable `character.player.png` /
`character.npc.person.png`. It does not revisit the design itself.

---

## 1. Current state

The visual/design axis is converged. Across the R&D pass and two subsequent
generation submissions, the following are settled and not in question here:

- 16×22 target cell, 3 columns × 4 rows, 48×88px total sheet
- four readable directions (`left, down, up, right`)
- soft-chibi proportions (head ≈ half height, capsule torso, stubby limbs)
- hoodie/backpack/jeans identity, warm two-tone jacket color-blocking
- the left/right silhouette-differentiation problem, substantially resolved
- pose/readability, substantially resolved

The production *method* has not converged. The last two submissions,
generated by prompting an image-generation model for a "pixel art" character
sheet, were measured at approximately **86,958–92,952 distinct colors** with a
**median color-run length of 1px**. True discrete pixel art at 16×22 has, by
construction, at most a few dozen colors and runs of several pixels wherever
a shape has flat interior fill. What was actually produced is continuous-tone
illustration — anti-aliased, gradient-shaded, JPEG/diffusion-textured — that
merely *resembles* pixel art at a glance and at small preview size.

This is not attributable to prompt wording. Two independent submissions from
the same generation pipeline produced the same failure mode at the same order
of magnitude. That is sufficient evidence that **the pipeline itself cannot
reliably produce discrete pixel data**, independent of how the prompt is
tuned. Continuing to iterate prompts against this pipeline is not expected to
change the outcome, and this document does not recommend another such run.

## 2. Requirements

Testable requirements, translated from the approved brief and art bible into
properties a QA script can check directly against a delivered PNG.

| # | Requirement | Source | Testable as |
|---|---|---|---|
| R1 | Sheet is exactly 48×88px at 1× authoring, or an integer multiple thereof at higher native resolution (e.g. 96×176, 192×352) | brief §12 | `width % 3 === 0 && height % 4 === 0 && width/3 === height/4 * (16/22)`-equivalent aspect check; exact 3:4 cell aspect (16:22) |
| R2 | Grid is exactly 3 columns × 4 rows, one 16×22-proportioned cell each | brief §1, §12 | slice sheet into 12 cells of `(width/3) × (height/4)`; each cell's aspect ratio must equal 16:22 |
| R3 | Row order is `left, down, up, right` | brief §12, `manifest.ts` `DIRECTIONS` | not machine-verifiable from pixels alone; enforced by construction/checklist, spot-checked by a human against the silhouette rules in R8 |
| R4 | Background is genuinely transparent (alpha channel), not a flat color fill | brief §3 requirements list | every pixel outside each cell's silhouette has alpha `< threshold` (e.g. 8); no cell has 0% or 100% transparent-pixel count (i.e., isn't accidentally opaque-filled or fully blank) |
| R5 | Discrete pixel colors — no continuous-tone/anti-aliased origin | this document, §1 | total unique RGBA colors across the sheet is small and bounded (see §6 thresholds); this is the core failure mode being guarded against |
| R6 | Limited palette | brief §7 | unique *opaque* colors per character sheet stays within a small cap (e.g. ≤ 24, matching "2–3 color blocks beyond skin/hair" plus outline/shadow steps) |
| R7 | No gradients | brief §7, §18 | no smooth ramps between adjacent same-region pixels; detected as an unusually high count of near-duplicate colors (see R9) rather than a few flat, repeated values |
| R8 | No anti-aliasing | this document, §1 | edge pixels are either fully opaque (belong to the silhouette) or fully transparent — no partial-alpha "soft edge" ring around shapes |
| R9 | No semi-transparent interior pixels | brief §3 ("transparent background required... no ground shadow baked in as opaque"), extended here | any pixel with `0 < alpha < 255` is flagged; a soft drop-shadow is the one allowed exception and must be alpha-only, never used inside the character silhouette itself |
| R10 | Readable silhouette, all four directions distinguishable, flattened to solid black | brief §3, §14.1 | automatable partially (silhouette bounding-box/shape diff between direction rows should be non-trivial, not near-identical); final call is human judgment per brief §14–§16 |
| R11 | Anchor consistency | brief §13 | lowest opaque pixel in each cell sits on the cell's bottom row; idle frame (column 1) horizontally centered on the cell's mid-column |
| R12 | Future animation compatibility | animation architecture, `assetLoader.ts` `resolveFrameSourceRect` | sheet dimensions divide evenly by the declared grid (R1/R2 already cover this); no requirement beyond what R1/R2 guarantee — the loader derives frame rects from decoded size ÷ grid, so nothing further is needed for `animation.ts` to slice it correctly |

Requirements R1, R2, R4, R5, R6, R8, R9, R11 are objectively machine-checkable
from the PNG's decoded pixel buffer alone. R3, R7, R10, and the qualitative
"reads as Soft Chibi" bar remain human/checklist judgment calls, same as the
existing brief §14–§16.

## 3. Production-method comparison

### A. Upscale-then-quantize (generate large, algorithmically downsample to true pixel art)

Generate the character at a large canvas (e.g. 512×704, preserving the 16:22
cell aspect at high resolution), then run it through a deterministic
quantize/downsample pipeline (nearest-neighbor or box-filter downsample to
16×22 per cell, followed by fixed-palette color quantization and alpha
thresholding).

- **Discrete pixel data:** guaranteed by construction — the final quantize
  step forces every pixel onto a fixed palette and forces alpha to 0/255.
  This is the step the last two submissions never actually went through;
  the model's raw output was accepted as final.
- **Silhouette preservation:** depends entirely on the *source* generation
  still being continuous-tone art, since the same generation pipeline that
  produced 87k–93k colors is still the source of the silhouette shape. Risk:
  downsampling a soft, blurry, ill-defined AI silhouette can produce mushy,
  inconsistent edges rather than the sharp shapes the brief requires.
- **Soft Chibi language:** preserved as well as the source generation
  preserves it — same risk as above, since design and production-method
  quality are now decoupled but not independent.
- **Direction reproducibility:** poor. The generation step must still be
  re-run per direction (or per full 3×4 sheet), and there is no guarantee the
  four directions downsample to consistent proportions/anchor points from
  independent generations.
- **Animation frames later:** same problem compounded ×3 per direction — a
  9-frame-plus walk cycle from independent generations is unlikely to hold a
  consistent silhouette across frames without heavy manual cleanup.
- **Engineering complexity:** low-to-medium — a downsample+quantize script is
  a well-understood, ~1-day build.
- **QA complexity:** same as any candidate — the §6 gates apply uniformly.
- **Automatable:** the quantize step, yes. The "does the silhouette still
  look right after downsampling" step, no — needs human review every run.
- **Maintainability for future NPC/enemy assets:** poor — every new
  character still depends on the same unreliable large-image generation step
  as its source of truth for silhouette quality; this approach fixes the
  *pixel-data* failure but not the *design-fidelity-per-run* failure, so it
  would need re-litigating per asset.

### B. Generated image as reference only, sprite reconstructed by hand/tooling

Use AI-generated imagery purely as a visual mood/shape reference (the same
role the R&D directions already play per the brief's own framing), then
construct the actual 16×22 sprite pixel-by-pixel — either by a human artist
tracing the reference in a pixel editor, or by a constrained
reconstruction tool that snaps a traced outline to a fixed grid and palette.

- **Discrete pixel data:** guaranteed — the sprite is authored as discrete
  pixels from the start; there is no continuous-tone intermediate to fail.
- **Silhouette preservation:** high — a human (or careful tool) is
  explicitly matching the approved reference's proportions and silhouette
  rules, with the brief's §2–§13 as an explicit checklist during
  construction, not an after-the-fact grade.
- **Soft Chibi language:** high, for the same reason — it's a construction
  target the whole time, not an emergent property of a generation model's
  training distribution.
- **Direction reproducibility:** high — all four directions are built
  against the same explicit ruleset (§3's mirror-image requirement for
  left/right, §4's hair-as-directional-signal rule) rather than four
  independent generations that may drift.
- **Animation frames later:** good — once the base pose vocabulary and
  palette exist, walk-cycle frames are incremental edits to the same sprite,
  which is exactly how pixel-art animation is normally produced.
- **Engineering complexity:** low if done by a human artist (no new tooling
  needed beyond what exists); medium-to-high if built as an automated
  "reconstruct from reference" tool, since faithfully vectorizing/snapping an
  arbitrary reference image to a clean silhouette is itself a hard,
  failure-prone problem — likely harder than the thing it's replacing.
- **QA complexity:** same fixed §6 gates as every method; simplest to pass
  because the artifact is discrete by construction.
- **Automatable:** the reconstruction-by-hand variant is not automatable (by
  design — that's the point). The reconstruction-by-tool variant is
  partially automatable but is its own R&D project.
- **Maintainability for future NPC/enemy assets:** good if a human artist
  is doing the construction (scales the way any pixel-art pipeline
  scales — cost is per-asset artist time, which is normal and predictable).
  Poor if pursuing the automated-reconstruction-tool variant, which adds a
  second unproven pipeline to maintain.

### C. Procedural/vector-free pixel data from a defined palette and silhouette spec

Construct the sprite directly as code — a `<canvas>` (or raw pixel-buffer)
script that paints an explicit, hand-specified set of filled shapes (head
disc, torso capsule, limb rects, hair mass) from a small fixed palette, per
direction, per frame — the same category of approach as the existing R&D
generator scripts (`generate-character-rnd.mjs`, `generate-pilot-art.mjs`),
but iterated with the specific fixes the brief already identifies (limb
contrast, left/right silhouette differentiation, hair-mass treatment).

- **Discrete pixel data:** guaranteed absolutely — there is no
  continuous-tone step anywhere in the pipeline; every pixel is either
  painted a palette color or left transparent by construction.
- **Silhouette preservation:** high, but bounded by the same ceiling the R&D
  pass already hit: procedural primitive-based construction can faithfully
  encode the brief's *proportions* (head ratio, capsule torso, limb
  placement) but has historically struggled with the *organic* polish a
  human artist or a good reference brings — this is explicitly why the
  brief's own framing (§19) says procedural construction "has not
  demonstrated it can reach the quality bar" on its own.
- **Soft Chibi language:** same ceiling — achievable at the level of
  correct proportions and color-blocking; less certain at the level of
  "looks hand-crafted and charming" rather than "looks like assembled
  primitives," which is a real, previously-observed gap (production brief
  §17's own critique of the R&D reference art).
- **Direction reproducibility:** excellent — a shared parametric function
  can guarantee left/right are literal mirror images (the brief's own
  explicit requirement, §3) and that up/down use a consistent proportion
  system, since all four directions come from the same code path with
  direction as a parameter.
- **Animation frames later:** excellent — this is the approach's strongest
  point. Walk-cycle frames are parametrized offsets (leg splay, arm swing,
  bounce) on the same shape functions, which is exactly what
  `generate-pilot-art.mjs`/`generate-character-rnd.mjs` already do
  successfully at the mechanical level.
- **Engineering complexity:** medium — the drawing code itself is already
  proven out by two prior R&D scripts; the work is refining shapes/palette
  to clear the quality bar, not building new infrastructure.
- **QA complexity:** lowest of all candidates — output is deterministic and
  discrete by construction, so the §6 gates should pass close to
  automatically; the only open question is the subjective §14–§16 quality
  bar, same as any method.
- **Automatable:** fully — this is a script, runnable in CI, requiring no
  external service, API key, or manual step for regeneration.
- **Maintainability for future NPC/enemy assets:** best of all candidates —
  a shared shape/palette function library means a new NPC skin is a
  parameter change (new jacket color, per brief §11), not a new production
  run through an external tool or a new manual construction pass. This is
  also the only approach that keeps character art inside the same
  repository, tooling, and review process as everything else already
  covered by `check-assets.mjs`/`manifest.test.ts`.

### D. External pixel-art generation/editing workflow

Use a tool purpose-built for pixel art (e.g. a dedicated pixel-art AI mode,
or a human artist using Aseprite/similar), demonstrated first on a small
sample to confirm it actually outputs discrete pixel data before committing
to it for the full character set.

- **Discrete pixel data:** genuinely capable tools (a real pixel-art editor,
  or an AI mode specifically constrained to an index-color palette) can
  guarantee this the same way approach B/C do — but this has to be verified
  per-tool before trusting it; "pixel art mode" branding does not itself
  prove the underlying data is discrete (the failure already observed came
  from a general image model that was simply asked to look like pixel art).
- **Silhouette/Soft Chibi/direction/animation:** all equivalent to a human
  artist's capability (approach B) if the workflow is a human using a real
  editor; equivalent to approach A's uncertainty if it's another AI
  generation step, however specialized, that still needs a downstream
  verification pass.
- **Engineering complexity:** low if it's a human artist workflow (no new
  code); unknown/variable if it's a new AI tool, since it requires
  integration and the same distrust-until-measured posture this whole
  document exists because of.
- **QA complexity:** identical fixed §6 gates.
- **Automatable:** no, if human-driven. Maybe, if AI-driven and verified —
  but "maybe, pending verification" is exactly the position the last two
  submissions started from.
- **Maintainability:** good if a named human artist/workflow is retained for
  future assets (normal cost of an art pipeline); otherwise inherits
  whatever risk the specific external tool carries, which is unknown until
  demonstrated.

### E. Hybrid: procedural construction, quantize-gated

Combine C and A's QA discipline: build the sprite procedurally (C), and run
every output — regardless of production method, including future ones —
through the same automated quantize/verification gate A implies (hard palette
snap, alpha thresholding, and the §6 checks) as a safety net, not as the
primary production step.

- This is not a fifth alternative "instead of" the others so much as a
  standing practice: whatever produces the pixels, verify them the same way.
  It costs nothing extra to adopt regardless of which primary method (C is
  recommended below) is chosen, and it is exactly the gate that was missing
  when the last two submissions shipped ungated continuous-tone output as if
  it were final.

## 4. Recommendation

**Procedural/vector-free pixel-data construction (approach C), with the
automated quantize/verification gate from approach E applied to every output
regardless of source.**

This is a reliability-first choice, not a novelty-first one:

- It is the only approach that makes "true discrete pixel data" a
  mathematical guarantee of the pipeline rather than a hoped-for property to
  be measured and possibly rejected after the fact. Every other candidate
  either depends on an unproven external generation step (A, D) or on
  recurring per-asset human labor with no automation ceiling (B, D).
- It reuses proven infrastructure. `generate-character-rnd.mjs` and
  `generate-pilot-art.mjs` already demonstrate this repository can paint
  procedural characters that pass the *mechanical* requirements (correct
  grid, transparent background, manifest-compatible file). The work
  remaining is exclusively on the *quality* axis the brief's §14–§16
  already define precisely — closing a known, scoped gap, not opening a new
  unknown one.
- It gives the best future-animation and future-NPC economics by a wide
  margin: parametrized shape functions turn a new walk frame or a new NPC
  skin into a code change, which is exactly the maintenance profile this
  project wants for "51 non-character manifest slots" and any future
  enemy/NPC variety, versus a recurring, unbounded cost per new asset under
  approaches A, B, or D.
- Its main historical weakness — procedural output looking "assembled" or
  "primitive" rather than hand-crafted — is a solvable design/shape-fidelity
  problem the R&D and pilot passes have already been iterating on
  successfully (per the brief's own account of Direction A improving over
  Direction C's rushed pilot). It is not the same category of problem as
  "the underlying pixel data isn't real pixel data," which has no
  design-iteration fix at all.

Approach B (human-authored, reference-guided) is the strongest fallback if
procedural construction cannot clear the brief's §14–§16 quality bar after a
genuinely serious attempt — it has the best design-fidelity ceiling of any
option. It is not the first recommendation only because it does not scale
automatically to NPC/enemy variety the way C does, and because C has not yet
been given a real attempt at the *specific, already-diagnosed* fixes (limb
contrast, left/right mirroring, hair-mass treatment) the brief calls out —
unlike the image-generation pipeline, which has now failed the same way
twice under real effort.

Approach A is not recommended as a primary method: it launders an unreliable
generation step through a quantizer, which fixes the measurable symptom
(color count) without fixing the actual problem (an AI model is still the
source of silhouette truth, and has not demonstrated it can hold that
silhouette steady). It remains useful as a component of the QA gate itself
(E) — quantize-and-measure is exactly how the 87k–93k color count in §1 was
caught — just not as the thing that decides the silhouette.

Approach D is not recommended until and unless a specific tool is named and
demonstrated on a small sample; it is not a decision this document can make
in the abstract.

## 5. Proposed pipeline

Reference → sprite construction → validation → gallery → integration, under
the recommended method:

1. **Reference (unchanged).** The already-approved Direction A R&D images
   (`docs/art/rnd/direction-a-soft-chibi-*.png`) and the production brief's
   §2–§13 construction rules remain the design source of truth. No new
   reference generation run is needed or recommended.
2. **Sprite construction.** A new generator script (sibling to
   `generate-character-rnd.mjs`/`generate-pilot-art.mjs`, e.g.
   `scripts/generate-character-production.mjs`) paints each of the 12 cells
   (4 directions × 3 frames) from explicit shape primitives and a small,
   named palette object (reusing `PALETTE` values from `world/draw.ts`
   wherever suitable, per brief §7), directly addressing the brief's
   already-diagnosed gaps:
   - left/right built as true mirror images from one profile definition,
     not independently drawn (closes §3's weakest pair)
   - a distinct limb color meeting the §6 hard contrast minimum, chosen and
     checked against `PALETTE.outline`/`PALETTE.ground` before drawing
   - hair silhouette treated as a first-class per-direction shape, not a
     head accessory, with the "up" row's unbroken solid mass as the
     template for how much the other three should also vary structurally
   - idle frame designed as a deliberate standing pose (brief §9), not a
     midpoint interpolation
3. **Automated validation (new).** A quantize/verification script (the
   approach-E gate) runs against the freshly generated PNG before it is
   treated as a candidate:
   - decode the PNG's actual pixel buffer (requires adding a PNG-decoding
     dependency — none exists in `static/package.json` today; `pngjs` is a
     reasonable, dependency-light choice)
   - run every §6 QA gate below
   - fail loudly and specifically (which gate, which cell, which pixel
     range) rather than a pass/fail bit, so a failure is actionable
4. **Human/native + gameplay-scale review.** The existing brief §14–§16
   checklist — native 16×22 silhouette read, four-direction distinguishability,
   walk-cycle-as-motion, gameplay-scale-in-context — stays a human judgment
   call, run against the automated-gate-passing candidate, not before it.
5. **Gallery.** Once a candidate passes both automated gates and human
   review, it is dropped into `public/art/<slot-id>.png` and reviewed in the
   existing `AssetGallery`/`assetgallery-main.tsx` tooling exactly the way
   Run 1's placeholder assets already are — no gallery changes needed, since
   the gallery already renders whatever is at that path.
6. **Integration.** `check-assets.mjs` already reports "real art" vs.
   "placeholder" per manifest slot with no changes needed; once
   `character.player.png` exists at the right path with the right
   dimensions, it is picked up automatically. Wiring the animation system
   into `world/draw.ts` (currently implemented and tested but not wired
   in, per the handoff §1) remains a separate, later decision, out of scope
   for this document and not something this document authorizes.

No step in this pipeline touches `world/draw.ts`, the manifest schema, the
loader, the animation architecture, or the gallery's code — it produces a
PNG file and validates it before it's dropped into the existing, unmodified
`public/art/` convention.

## 6. QA gates

Objective, automatable checks against the resulting PNG's decoded pixel
buffer (a script requirement, not yet built — see §7):

| Gate | Check | Pass condition |
|---|---|---|
| **Dimensions** | decoded width/height | width is a multiple of 3, height a multiple of 4, and `(width/3):(height/4) == 16:22` |
| **Grid/cell count** | slice into `cols=3, rows=4` per `frames` declaration | exactly 12 cells, each cell's aspect ratio matching 16:22 within rounding |
| **Transparency behavior** | per-pixel alpha histogram | every pixel is alpha `0` or alpha `255` — no value strictly between (catches anti-aliased edges and soft/gradient fills); at least one fully-transparent and one fully-opaque pixel per cell (catches an accidentally all-opaque or all-blank cell) |
| **Unique color count** | count of distinct opaque RGBA tuples across the whole sheet | small, fixed ceiling (e.g. ≤ 24 for the whole sheet, matching brief §7's "2–3 color blocks beyond skin/hair" plus outline/shadow/hair/skin) — this is the single gate that would have caught the 87k–93k-color failure immediately |
| **Color-run characteristics** | for each row of pixels within each cell, measure run-lengths of identical colors | median run length must clear a floor (e.g. ≥ 2px) — catches per-pixel-dithered or noisy output that happens to use few colors but never in contiguous blocks |
| **Palette consistency** | compare each frame's/direction's color set against the sheet's declared palette | no frame introduces a color outside the declared set (catches drift between hand-tuned or independently-generated frames) |
| **Anchor consistency** | lowest-opaque-pixel row per cell | equal across all 12 cells (every cell's feet sit on the same bottom row); idle-column (col 1) horizontal opaque-pixel centroid within ~1px of the cell's horizontal center |
| **Accidental anti-aliasing / near-duplicate colors** | pairwise color distance (e.g. simple Euclidean in RGB) between all colors in the palette | no two colors closer than a minimum distance threshold *unless* deliberately paired as a color/its-own-outline step (an explicit allow-list of intentional pairs, e.g. jacket-main/jacket-shadow) — catches near-duplicate colors that are really anti-aliasing artifacts masquerading as "few colors" |
| **Direction completeness** | 4 distinct silhouettes (flattened to opaque-mask-only, ignoring color) compared row-to-row | no two of the four direction rows produce an identical opaque-pixel mask (a trivial recolor-only "direction" fails this); left/right masks are horizontal mirrors of each other within a small pixel-count tolerance |

These gates are necessary, automatable, and objective — they replace "does
this look like pixel art" with "is this discrete pixel data," which is
exactly the axis the last two submissions failed on without anyone having a
script that could have caught it before human review. They do not replace
brief §14–§16's human judgment calls (does it read as Soft Chibi, does the
walk cycle read as motion) — those stay manual.

## 7. Next implementation step

**Build the automated QA/quantize-verification script first, run it against
the existing failed submissions to confirm it actually catches their known
failure, then use it as the acceptance gate for the first procedural
production run.**

Concretely: add a PNG-decoding dependency to `static/package.json` (e.g.
`pngjs`, dev-only, no runtime impact) and write
`scripts/check-character-art-quality.mjs` implementing the §6 gates above,
taking a PNG path and the expected `frames` grid as input, and printing a
pass/fail report per gate (mirroring `check-assets.mjs`'s existing
reporting style). Validate it against one of the two already-rejected
submissions to confirm it reports the known ~87k–93k unique-color failure
correctly before trusting it as a gate for new output.

This step touches only `static/package.json` (a new devDependency) and a new
file under `static/scripts/`. It does not touch gameplay, `world/draw.ts`,
the manifest, the loader, the animation architecture, the gallery, or any
existing validation tooling — it is purely additive and can be built and
verified in complete isolation before any new character-art generation run
is attempted.

Only after that script exists and is confirmed to correctly reject the two
known-bad submissions does it make sense to spend a production run on the
procedural construction approach (§5 step 2) — running new art through an
unproven gate would repeat exactly the mistake this document exists to
correct.
